# IFIP registration and enrollment audit

Source audit, 11 November 2026. Scope runs from the public application links through first dashboard access and includes existing waitlist, interrupted checkout, and credential recovery paths. Partner intake and internship applications are separate flows. Homepage and dashboard links are integration boundaries for this phase.

## Repository context

The initial audit used `ifip-frontend/AGENTS.md` and `ifip-frontend/CLAUDE.md`. The root instructions and project-wide documents were absent at the start of that audit. They are now available through the [project instructions](../../../AGENTS.md). The [shared design system](../DESIGN.md) uses existing IFIP tokens provisionally and records how the local Dribbble reference informs the public site.

IFIP uses Next.js App Router, React, Tailwind CSS, Sora/Georgia, Axios and Zod on the frontend, and Express, MongoDB and Redis on the backend. Existing integrations include Brevo email, Cloudinary, Flutterwave, and Paystack verification support. The review applies `better-interface`, `better-layout`, `better-typography`, `better-accessibility`, `better-ui`, `better-colors`, and `better-writing` to the source. `state-machine` informed the state inventory. Its scratch route and mock-data workflow conflicts with this phase. `shadcn` informed component composition, with native controls as the baseline because the app has no `components.json` or installed shadcn UI primitives. `interface-review` is reserved for the future implementation diff, since the current scope is the existing journey.

## Routes and entry points

| Route | Existing responsibility and components |
| --- | --- |
| `/`, `/about`, `/login` | Public links to `/apply`. Homepage links appear in `HeroSection`, `HomeNav`, `MobileBottomNav`, `PlacementsSection`, and the page CTA. About and login supply additional links. Email templates and reminder messages also link to `/apply`. |
| `/apply` | `app/apply/page.tsx` renders availability, waitlist, resume, verification, personal profile, academic background, program interest, skills and motivation, levy and declaration, and the step 7 confirmation. `?token=` starts email-link resume. `?payment=verified` is a payment-return hint. |
| `/apply/resume` | `ResumeRedirect` forwards the token to `/apply?token=…`, or forwards to `/apply` without a token. Current resume and payment-recovery emails primarily link directly to `/apply?token=…`. |
| `/verify-payment` | `VerifyPaymentContent` reads the provider callback and stored polling credentials, then polls payment status. Hosted checkout is an external provider surface. |
| `/set-password` | Token-based account setup shared with invited users. Reads display context and submits the new password. |
| `/login`, `/forgot-password`, `/reset-password` | Returning login, MFA challenge where required, inline and standalone reset requests, and emailed reset-link completion. |
| `/dashboard`, `/partner-portal`, `/admin` | Existing authenticated landing routes. Registration normally leads to the participant dashboard. Shared auth routes also serve partner and admin roles. |

## Actual sequence

1. `/apply` requests registration availability while independently checking resume credentials and geolocation. The public availability endpoint finds an `upcoming` cohort whose registration dates include the current time, then calculates its remaining capacity. Applicants do not select a cohort. The checkout handler selects and attaches the then-active cohort. No active cohort and full cohort both lead to the waitlist in the current UI. The waitlist records a normalized email and returns 409 for an existing entry.
2. An applicant enters an email and requests a six-digit code. `/applicants/start` checks a separate global capacity calculation and existing accounts. Rate limits apply before the handler. It stores the code hash in Redis with a configurable expiry (10 minutes by default), then triggers email. The UI starts a 60-second resend cooldown. A resend replaces the pending code. Existing accounts are directed to login by the API message.
3. Correct OTP creates or reuses an `Applicant`, rotates its resume token, removes the OTP, emails the resume link, and returns a separate applicant session token. The browser stores `applicantToken`, advances to profile, and makes a best-effort step-index save. An existing link exchanges its token for a session and hydrates saved fields. Same-browser return fetches `/applicants/me`; both paths restore `isPaid`. Email-link resume clamps the step to at least 2, while same-browser resume uses the saved index as returned.
4. **Personal profile → Academic background → Program interest → Skills and motivation.** Each successful Continue validates the current step with Zod and PATCHes the accumulated profile and next `currentStep`. Back changes local navigation. In-step edits are not guaranteed saved. Academic and interest options use the existing form-options/cache hook. CV selection triggers upload immediately. The application service requests a Cloudinary signature, attempts direct upload and saves the URL, with a multipart backend fallback for a direct-upload failure.
5. In **Payment and declaration**, the applicant can validate or remove an optional coupon. The displayed levy and discount are calculated locally. The checkout handler revalidates coupon availability, selects cohort, checks capacity, records `checkoutStartedAt`, and calculates the charge from residence country, configured price, and discount. The normal UI saves the signed declaration and levy acknowledgment **before** initiating checkout. Capacity includes qualifying applications, paid drafts, and checkout starts within 15 minutes. The timestamp is not evidence of a guaranteed reservation.
6. Standard and partial-discount payments start a hosted Flutterwave checkout. The browser saves `paymentReference` and `paymentPollingToken` before leaving. Paystack verification and webhook handlers remain in the code. A full waiver records a zero-value successful payment and bypasses the gateway. The UI jumps to inline confirmation, using a setup token if returned.
7. On hosted return, `/verify-payment` accepts `reference`, `trxref`, or `tx_ref`, optional provider transaction ID and status, and the local polling token. It checks immediately and schedules checks every two seconds up to 20 attempts. The backend can verify directly while awaiting webhook delivery. Gateway-return cancellation/failure, backend failure, missing credentials, timeout, and repeated request errors all use the current failed UI. Success clears the polling credentials. A setup token routes to `/set-password`. Success without it routes to `/apply?payment=verified`, where the draft can be hydrated and a paid application submitted.
8. Confirmed payment can trigger enrollment automatically when the saved declaration is signed. The shared operation creates or finds the user, creates the permanent `Application` as `active`, sets the participant role, links the payment, emits setup/enrollment messages, and deletes the draft. Older or interrupted paid drafts can finish via `/applicants/submit` after valid declaration and successful payment. Support/admin paths include manual payments, payment resolution, applicant reminders, and setup-link resend. They use separate administrative entry points.
9. Manual final submit shows step 7 with the setup action if present. Normal hosted success with a setup token skips step 7. `/set-password` submits the token and password, then stores credentials through the auth helper and continues to `/dashboard` for participants or `/partner-portal` for partners. Returning sign-in routes by role and supports MFA. Forgot/reset routes provide the existing password recovery path. A saved draft has no automatic document TTL in `Applicants.ts`. OTP, applicant session, polling token (30 minutes), and reset token have independent lifetimes. Resume links depend on the stored hash and draft existence. The current setup-token signer sets no explicit expiry; the UI should avoid inventing a countdown.

## API dependencies

Express prefixes these routes with `/api/v1`. The geolocation route is served by Next.js. `ifip-frontend/lib/api/services.ts`, `auth.ts`, `client.ts`, and `lib/hooks/useFormOptions.ts` are the frontend integration points.

| API | Contract in use |
| --- | --- |
| `GET /cohort/registration-status` | `hasActiveCohort`, `isFull`, and optional cohort name, end date, cap, count, brochure. Cache headers allow stale responses. The separate `GET /applicants/cohort-status` uses global capacity and is not the `/apply` entry check. |
| `GET /api/geolocation` | Country, region and city hints from headers. Defaults to NG when unavailable. |
| `POST /applicants/start`, `POST /applicants/verify-otp` | Email and email/code respectively. Verification returns `{ sessionToken, applicant }`. |
| `POST /applicants/resume`, `GET/PATCH /applicants/me` | Exchange `{ token }` for session and applicant, then read/save with applicant bearer token. PATCH whitelists form and step fields. |
| `GET /form-options?group=…`, `GET /content-versions` | Academic status and placement interests through the cached hook. |
| `GET /uploads/signature`, `POST /uploads/save-cv`, `POST /uploads/cv` | Signed Cloudinary upload, URL persistence, multipart fallback. |
| `POST /payments/coupon/validate`, `POST /payments/initiate` | Applicant bearer token. Coupon code and optional checkout coupon respectively. Initiation returns gateway URL/reference/polling token or waiver bypass/reference/optional setup token. |
| `GET /payments/:reference/status`, `POST /payments/webhook/{flutterwave,paystack}` | Poll token tied to reference. Polling returns `pending`, `success`, or `failed`, with optional setup token. Provider callbacks and polling can reach overlapping enrollment logic. |
| `POST /applicants/submit` | Applicant session, complete draft and successful linked payment. Success can return the setup token. |
| `GET /auth/token-info`, `POST /auth/set-password`, `POST /auth/login`, `POST /auth/login/mfa-verify`, `POST /auth/refresh` | Existing account context, setup, role/MFA login and refresh contracts. |
| `POST /auth/forgot-password`, `POST /auth/reset-password`, `POST /waitlist` | Existing password recovery and waitlist contracts. Password request deliberately returns generic success. |

## Existing workflow states

| State owner | States observed or represented by existing branches |
| --- | --- |
| Availability | Checking → open or combined closed/full. Request failure logs an error and leaves the initial/open-looking UI. |
| Verification and resume | Email entry → sending → code entry/cooldown → verifying → profile. Invalid, expired, throttled, unavailable, or existing-account responses. Link/session restoration can resolve, fail, or offer a connection retry. |
| Application | Steps 2–5 editing → validating → saving → next step. Failure stays on current step. Upload is independent and may be empty, uploading, stored, or failed. |
| Checkout | No coupon → validating → applied/rejected/removed. Declaration editing → saving → initiating → redirect or waiver. Paid draft → submitting → confirmed/error. |
| Payment | Verifying → pending, paid with setup link, paid without setup link, or failure UI. The latter collapses confirmed failure and unknown outcomes. |
| Enrollment | Draft, paid draft, permanent application plus linked payment, setup pending or authenticated. Separate records can disagree during partial failure. |
| Auth and waitlist | Setup token loading/ready/invalid, password submitting/success/error, login/MFA/recovery. Waitlist input/submitting/joined/error including already joined. |

## Ranked UX findings

Frontend locations beginning with `app/` or `lib/` are relative to `ifip-frontend/`. Controller locations are relative to `ifip-backend/src/`. Rendered layout, computed contrast, keyboard and screen-reader behavior remain unverified. The contrast below is calculated for the declared opaque color pair.

| Severity | Domain | Evidence and user impact | Redesign response |
| --- | --- | --- | --- |
| High | Writing | `app/verify-payment/page.tsx:25–105,142–170` treats missing session, pending timeout, network failure and confirmed failure as one failed screen. The return action may send someone who already paid back toward checkout. | Name the known outcome and next step. Use verification or support for an unknown outcome. |
| High | Writing | `app/apply/page.tsx:1194–1202,2987` treats a waiver as application submitted even when no setup token is returned. | Medium | Layout | `app/apply/page.tsx:2768–2968` puts summary, security card, coupon, terms and declaration in one dense step. | Medium | Writing | `app/apply/resume/page.tsx:18–30` has a spinner and blank Suspense fallback. `/apply` includes inconsistent landing behavior for invalid email links vs stale local sessions. | Give the redirect a named status and use existing email verification or support as recovery. |
| Medium | Writing | `app/set-password/page.tsx:107–155,344,393–395`, `app/login/page.tsx:604–607`, `app/forgot-password/page.tsx:176–178`, `app/reset-password/page.tsx:73–120,308–309` contain timed navigation or placeholder links. The set/reset forms separate client link checks from server errors. | Keep accessible confirmation and an explicit onward action with the existing destination. Use verified destinations for support and legal links. Preserve shared role behavior. |

Other step-specific friction informs the form spec. The personal form uses a restrictive ASCII name rule and split date selectors. Academic options can be loading or unavailable while users need to choose a status. Program interest describes a singular primary choice while its handler stores an array. Skills uses comma-separated input and has conditional internship description plus CV upload. The waitlist implies academic/professional email is required although the server only validates email shape. Its duplicate response should read as an already-joined state. Source evidence is in `app/apply/page.tsx:1790–2688,1444–1556`, `lib/validation/applySchemas.ts`, and `controllers/waitlistController.ts`.

## Regression risks and separate approvals

| Risk | Required boundary |
| --- | --- |
| Global OTP capacity and per-cohort registration/checkout capacity can disagree. Checkout checks capacity before writing its timestamp, and selection occurs again at checkout. | Preserve selection, counts, dates and reservation policy. Backend approval for a canonical availability or atomic reservation rule. |
| Provider callback hints, polling, webhooks, manual resolution, and waivers can race. Provider evidence, replay and transition ordering need review. | Backend approval for verification, duplicate payment prevention, authoritative reconciliation and any payment-state changes. Frontend pending guards only cover the active UI. |
| `Payment.success`, `Applicant.isPaid`, linked application, participant role and email delivery are separate writes/effects. Repeated handlers can short-circuit after success even when enrollment failed. | Backend approval for recoverable/idempotent enrollment, coupon consumption consistency, backfill or delivery retry. UI must work with the existing optional setup token. |
| Client price defaults and whole-currency rounding can diverge from configured server minor units. Residence also controls currency. | Preserve actual calculation at checkout. Use estimate wording for the current display. An authoritative pre-checkout quote needs separate approval. |
| Resume and auth use different credentials. Token invalidation, OTP resend/expiry, password token rules, role redirects, and session persistence affect other entry points. | Preserve endpoints and token handling. Backend approval for lifecycle, verification or recovery changes. Existing password, legal and applicant eligibility rules remain in force. |
| Browser storage and cached availability may be stale after reload, interruption or another tab. Existing draft retention and legacy paid drafts are easy to regress. | Exercise fresh, resumed and paid sessions with real staging API responses before release. Avoid inferring payment from a query string or inventing a guaranteed reservation or recovery API. |
